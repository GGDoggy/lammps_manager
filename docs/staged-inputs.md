# Staged input preparation

T007 implements input snapshots and authenticated transfer between distinct local roots. T008 adds staged execution and [durable result collection](staged-results.md). Shared execution remains available.

## Configuration and commands

Use the existing `submit`, `serve`, `worker`, `status` and `inspect` commands. On the manager, set `storage.mode: staged`; on each worker, set top-level `storage_mode: staged`. Set `storage.work_root` on the manager and `work_root` on the worker to their respective absolute local directories. Create these roots before service startup. SQLite and worker journals remain on local durable storage. Authentication, TLS, private credentials and redirect/proxy restrictions are unchanged; see [workers.md](workers.md).

Both manager storage and worker configuration accept these positive integer limits:

| Setting | Default |
|---|---:|
| `max_input_files` | 10000 |
| `max_input_file_bytes` | 1073741824 |
| `max_input_total_bytes` | 10737418240 |

The manager settings live under `storage`; worker limits are top-level. Submission and downloads enforce manager limits; workers independently enforce their own limits before downloading. Limits count regular files, including empty files, and sum their bytes. They do not include directory entries. Changing limits does not rewrite previously submitted specifications; smaller limits can defer an existing transfer with an explicit reason. Empty directories are not transferred. Inputs must be a nonempty tree of regular files and directories; symlinks and special files are rejected. Input manifest paths are canonical relative POSIX paths; traversal, absolute paths, duplicate entries and file/directory conflicts are rejected. Service accounts must protect local roots and journals from other writers.

Submission copies all regular files, including auxiliary data and potential files, into manager-local `JOB/inputs`. The staged specification records `storage_mode` and an immutable `input_manifest` of relative path, size and SHA-256 for every file. Hashes describe the copied bytes, including the primary LAMMPS input. Source changes after submission do not affect snapshots. Copying uses bounded chunks and rejects files that change size during copying. Submission is not a transaction over an externally mutable source tree: stop source writers if a consistent multi-file scientific dataset is required. A submission failure may leave unpublished manager directories; it never launches a simulation.

## Protocol and transfer guarantees

Staged polls require `protocol: 2` and `storage_mode: staged`; responses identify both. Mixed modes or older staged peers fail explicitly with HTTP 409; current workers surface a storage protocol error. Legacy shared workers can continue using the shared challenge protocol. Mode selection applies to new submissions. Existing shared snapshots keep their mode, and the scheduler records `storage_mode_mismatch` instead of assigning them through a staged manager. Process recovery and changing the storage mode of existing jobs are outside T007.

Each artifact uses an authenticated `GET /v2/inputs/ATTEMPT/files/INDEX`, with the same worker ID and bearer credential as polls. The manager checks registered credentials and assigned-attempt ownership, then selects the manifest entry by index. No client-supplied filesystem path is opened. The service caches up to 32 successfully validated immutable specifications using LRU eviction, keyed by database, job and input limits. Concurrent downloads share validation work; changed limits require validation again. Every request still checks current attempt ownership/state and safely opens and checks the selected file. Files are streamed in chunks of at most 64 KiB with declared content lengths and a 10-second socket timeout. Files stay outside poll JSON. Both ends reject symlinks when opening inputs. The worker verifies exact size and SHA-256 before publishing any inputs. A manager snapshot changed on disk therefore cannot silently become a valid worker input.

The worker durably records the original specification and assignment before transfer. Manager paths remain in the immutable specification. Its runtime attempt directory is `WORKER_ROOT/JOB/ATTEMPT`, with inputs under `inputs`. The additive SQLite `input_transfers` table records local paths, `downloading`, `failed` or `ready`, and a diagnostic reason. Manager polls mirror this record for `inspect`. These are transfer states, separate from process state. Failed transfer leaves the attempt assigned and its reservation intact, without claiming termination. Restart or replay retries transfer, never execution. An already published tree is verified rather than overwritten if publication preceded the journal update.

Downloads use a fresh hidden temporary directory under the attempt directory. All files and directory entries are flushed before atomic rename to `inputs`; the complete ancestor directory chain is flushed bottom-up through the filesystem root before recording readiness. Replaying an existing publication verifies its contents and flushes the same ancestor chain again: directories left by a failed attempt are not assumed durable merely because they exist. A failed sync at any ancestor keeps the transfer failed until synchronization succeeds, without redownloading verified published inputs. Missing, interrupted, oversized or corrupt downloads never publish a partial input tree. Handled failures remove only their temporary download directory. A process crash may leave an abandoned hidden temporary tree, which is never used as ready input. No simulation output or historical attempt is automatically deleted.

A ready transfer remains assigned until the worker verifies resource availability, receives manager result capability (`staged_launch_enabled: true`, `results_protocol: 1`), and durably claims the launch right. The executor verifies the complete input manifest into a separate `work` tree before launching. `run-local` still defers staged snapshots: use polling workers for staged execution. Older managers without result capability allow input preparation only; older T007 workers retain their executor guard. See [staged results](staged-results.md) for recovery, publication and retention.

Input downloads run synchronously within their worker's poll cycle, so large input transfers can delay that worker's heartbeats; no timeout releases reservations or triggers reassignment. Result enumeration, hashing, uploads and commit replay run in a dedicated single-thread executor independently of polling and process execution, so slow result collection does not block heartbeats, cancellation delivery or recovered-process time-limit checks. See [staged results](staged-results.md) for acknowledgement ordering and shutdown behavior. The manager handles HTTP requests in separate threads: artifact streaming holds no poll lock. Separate locks serialize poll/scheduling state and result operations respectively. Closing the server waits for active request handlers. Deployment and real transfer performance remain T009.

## Compatibility and verification

T006 migrates database schema version 1 to version 2 for multiple attempts; input-transfer records are preserved. Opening an existing database transactionally creates `input_transfers` if absent, without rewriting jobs or attempts. Old specification JSON without the new fields decodes as `shared` with an empty manifest; identical submissions remain idempotent without rewriting old JSON. Shared worker journal identities are unchanged. Staged identities additionally bind storage mode and protocol version; reuse with another mode fails rather than losing duplicate-execution fences. Restart with the original journal and roots.

`tests/test_staging.py` covers full snapshots, limits, unsafe paths and types, old database migration, distinct roots, authentication and ownership, missing/corrupt/interrupted downloads, disk failures, retry/restart/publication replay, runtime symlink rejection, incompatible protocol and mode, and input preparation independently of launch. Existing shared fake-process tests remain in `make check`. T008 result tests add local staged execution and result recovery coverage. These local tests do not verify real hosts, MPI / LAMMPS or real-host running-process recovery.
