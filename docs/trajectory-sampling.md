# Global trajectory sampling and lossless compression (T024)

New built-in ABP runs use immutable global sampling. All built-in contract
versions support a `sampling` request; existing submitted snapshots retain their
original scripts and output policy. Omitting the setting for a new run selects
`{"unit":"Dr","interval":0.01,"count":30000}`. Here Dr=kBT/gamma_r,
and a dimensionless position u maps to `floor(u/(Dr*dt)+0.5)`.
Decimal round-half-up uses the submitted decimal values. Rounded step zero,
duplicate steps, non-increasing positions and engine-overflow values fail
submission. Requested steps must also be exactly representable by LAMMPS's
binary64 equal-style variable. At most 1000000 points are accepted.

For `submit-run`, either use an interval/count or explicit positions:

```json
"sampling": {"unit": "Dr", "positions": [0.01, 0.02, 0.05, 300.01]}
```

```json
"sampling": {"unit": "step", "interval": 100, "count": 40000}
```

```json
"sampling": {"unit": "step", "positions": [1, 10, 100, 1000]}
```

There is no special cutoff at point 30000: an explicitly extended schedule keeps
producing output. Points beyond the submitted production duration are retained
as intent but never executed. Each segment selects points strictly after its
global start and at or before its end. `initial.dump` records the original state
once in the first segment; production `trajectory.dump` contains no extra segment
initial frame. Both use `id x y ix iy mux muy muz` and `%.17g` float formatting.
The two-step restart smoke retains independent dump files/settings and restores
the initial state before production.

The run snapshot and each job specification bind the schedule. Immutable input
manifests hash `sampling.json`, `sampling.lmp` and `snapshot-steps.txt` along with
the primary script. The step file ends with a guard beyond the command end
(normally end+1, rounded upward if needed for binary64 representation) so LAMMPS
can evaluate its next requested step after the last production frame without
exhausting the file. The guard is not a requested sample. A segment with no
samples creates no production dump. Long segments split into engine run commands
receive separate `sampling-000001.lmp` / `snapshot-steps-000001.txt` files, and so
on. The renderer closes and reopens the dump in append mode at each command,
preventing a second run setup from consuming and skipping a future sample.
Launch verification checks generated bytes
against the immutable request, including retries and successors.

This uses LAMMPS [variable-driven dump scheduling](https://docs.lammps.org/dump_modify.html)
and [write_dump](https://docs.lammps.org/write_dump.html). The existing build
inventory/restart fences remain required; local fake-engine tests alone do not
establish scientific or real-build acceptance.

## User-supplied scripts and sweeps

`submit` batch entries and `submit-sweep` manifests optionally accept the same
sampling fields, plus explicit `dt`, `Dr` and `total_steps`:

```json
"sampling": {
  "unit": "Dr", "interval": 0.01, "count": 40000,
  "dt": 0.0001, "Dr": 1.0, "total_steps": 4000000
}
```

The source script must contain a standalone `include sampling.lmp` after atom
initialization and before the production run. Remove its own trajectory dump
definition and use the declared global zero-to-total_steps production interval.
For durations over the engine's single-command limit (2^31-1), split production
into that many steps per command plus the final remainder and include each
numbered sampling file immediately before its corresponding later command.
It must provide the ABP atom fields used by the include. The manager does not
parse arbitrary scripts to infer physics, rewrite run commands or prove the
declared duration; these remain the script author's responsibility. Reserved
generated filenames must not already exist in the source. Source files are
preserved, and the generated files join the immutable per-job input manifest.

## Compression and delivery

After confirmed process/session termination, result collection streams each
`work/**/*.dump` through Python gzip with deterministic headers. It computes the
original SHA-256/size, streams decompression and checks the restored identity,
then rereads the original to reject changes. Only then can the archive be
published and the result manifest be bound. Restart checkpoints, logs and non-dump inputs
keep their original formats. This is byte-preserving compression; numeric text
is not parsed or reformatted. Memory use is bounded by transfer chunks, not file
size. Original trajectories remain on the worker until acknowledged cleanup.

An archive is selected only when its byte savings exceed the added UTF-8 JSON
manifest cost: the changed file entry, gzip/original identity record, field/list
wrapper and separator. Each file conservatively pays for the whole wrapper;
MPI selection also charges for the manager's participant path prefixes. Thus
selected artifacts plus their serialized manifest are strictly smaller than the
equivalent raw delivery whenever compression is selected. This compares logical
delivered bytes, not filesystem allocation, repeated HTTP requests or transient
worker storage: verification temporarily needs both representations, and the
existing original-retention and acknowledgement gates still apply. Empty,
incompressible and metadata-dominated trajectories remain raw, with no newly
published archive. Mixed raw/gzip deliveries are supported. Previously bound
manifests retain their immutable selection.

The manifest's `files` list selects beneficial `.dump.gz` archives instead of raw dumps.
Its optional `compression` list records the archive path, size, SHA-256, gzip
codec and original path/size/SHA-256. Transfer limits apply to the selected
compressed results. Plain old manifests remain accepted. Failed compression,
verification or conflicting destination files fail collection visibly and retain
the original; they do not trigger another simulation. Before manifest binding,
replay regenerates deterministic gzip bytes and accepts only an identical
existing archive. Once bound, existing immutable delivery/retry rules apply.

Polling workers publish shared and staged results through the authenticated
durable manifest/upload/commit protocol. Multi-host participants perform the
same post-termination compression and retain original identities in the combined
manifest. `run-local` verifies and publishes a local `results/` tree before
marking delivery collected. Shared/local data is retained; staged worker cleanup
still requires the durable manager acknowledgement and existing ownership checks.
Compression failure never authorizes cleanup. No deployment is changed by these
source changes.
